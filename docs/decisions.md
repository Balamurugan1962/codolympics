# Decision Ledger

Every architectural and design decision made for this project, with the reasoning.
Decisions here are settled; open questions are listed at the end.

**Related:** [contest-rules.md](contest-rules.md) · [requirements-judge.md](requirements-judge.md) · [requirements-backend.md](requirements-backend.md) · [requirements-frontend.md](requirements-frontend.md)

## Engine and architecture

| # | Decision | Reasoning |
|---|---|---|
| 1 | **go-judge** as the execution engine | MIT licensed, cgroup v2 native, multi-arch, actively developed, and its file cache makes compile-once/run-many natural |
| 2 | **Not Judge0** | Its schema has a single `stdin` column, so it cannot compile once and run many — 10k testcases would mean 10k compiles. Also cgroup v1 only, no release since Apr 2024, GPL-3, amd64-only |
| 3 | **Not DOMjudge** | Excellent and modern, but has no concept of per-participant question ownership, which this contest requires |
| 4 | Judge is **two containers** — `judge-api` unprivileged, `go-judge` privileged with no published ports | go-judge has no authentication; anything that reaches it can run code in a privileged container |
| 5 | ~~Six services~~ → **four**: Next.js (UI + API), judge-api, go-judge, Postgres | Superseded by decision 62. Sessions live in Postgres, the submission queue is a database poller, and SSE fanout is in-process — nothing was left for Redis to do |
| 6 | **Judge is stateless** — no database, no Redis | A restart loses only in-flight jobs; the backend stores every submission |
| 7 | **Deployment topology deliberately undecided** | Nothing may assume backend and judge share a filesystem |

## Judge API

| # | Decision | Reasoning |
|---|---|---|
| 8 | **Polling, not synchronous** | A correct solution running near a 1s limit across many testcases can exceed nginx's 60s default timeout — precisely the submissions that deserve to pass |
| 9 | `POST /submit` → `202` + job handle | |
| 10 | `GET /jobs/{id}` with `progress.done/total` | A long judgement with no feedback causes resubmission, doubling load |
| 11 | `DELETE /jobs/{id}` | Cancels superseded jobs so slots aren't wasted on unread verdicts |
| 12 | `GET /problems` | The admin dashboard's "file manager" view |
| 13 | `POST /problems/{id}/validate` | Runs the reference solution over every testcase |
| 14 | `GET /problems/{id}/testcases/{index}?version=` | **Administrator/jury use only** — for resolving disputes, never sold to participants |
| 15 | **Non-AC verdicts are HTTP 200** | A wrong answer means judging *succeeded* |
| 16 | **`IE` is a verdict, not an HTTP error** | Infrastructure failure must never be scored against a participant |
| 17 | **`problem_version` on every judgement** | Rejudge disputes are unresolvable without knowing what was actually judged |
| 18 | **`jury_detail` is admin-only** | It contains the expected answer; hints are *bought* here |
| 19 | Validated **OpenAPI 3.1** contract | The backend can be built before the judge exists |

## Languages and limits

| # | Decision | Reasoning |
|---|---|---|
| 20 | C, C++, Python, Java, JavaScript, **PyPy** | Measured: C++ 89.6%, Python 5.0%, Java 3.4%, C 1.6% of Codeforces submissions — 99.6% coverage |
| 21 | **No per-language time multipliers** | Authentic Codeforces behaviour |
| 22 | **1 second** limit | Codeforces standard |
| 23 | **PyPy added** | The standard escape hatch, and it matters more here: a Python-only owner who cannot fit 1s loses the question entirely, and nobody else can attempt it |

## Judging behaviour

| # | Decision | Reasoning |
|---|---|---|
| 24 | **Compile once, run many** | The reason Judge0 was rejected |
| 25 | **Early exit** at first failure | Most submissions are wrong; this makes them ~7× cheaper |
| 26 | Zero-padded filenames, sorted | "Test 12" must mean the same testcase on every rejudge |
| 27 | **The sandbox never sees the testcase directory** | Inputs arrive as stdin, so even a sandbox escape reaches no testcases |
| 28 | cpuset pinning, bounded parallelism | The tiebreak is speed, so measured times must be reproducible |

## Problem authoring

| # | Decision | Reasoning |
|---|---|---|
| 29 | **Own package format**, not Kattis/ICPC | Kattis has no place for priced text hints and assumes C++ testlib validators |
| 30 | **stdin/stdout programs**, not function stubs | HackerRank-style stubs need per-language boilerplate for every problem |
| 31 | Named comparators: `tokens`, `exact`, `float`+tolerance, `yesno` | Most problems need no checker code at all; float tolerance is the usual "hard" case |
| 32 | **Python checkers**, no testlib | testlib C++ is too high a barrier for student problem setters |
| 33 | **Python validators**, optional per problem | Nearly free once the Python reader API exists |
| 34 | **Reference solution required** per problem | Answer files are generated by *some* solution; if it had a bug, every answer is wrong |
| 35 | Free **samples**, shown and judged first | Without them, the first hint purchase is spent discovering the output format |
| 36 | Versioned directories + **atomic symlink swap** | Judging must never see a half-written problem |

## Storage

| # | Decision | Reasoning |
|---|---|---|
| 37 | Local disk behind a narrow `TestcaseStore` interface | Keeps `docker compose up` working with no setup, while leaving the door open |
| 38 | `S3Store` with a **local cache**, later | HackerRank measured S3 GETs at 50–100ms; 100 testcases would add 5–10s per submission |
| 39 | **No MinIO** | `minio/minio` and `minio/mc` were both archived in 2026 |
| 40 | **No separate file-manager service** | S3 replaces the reason for one; the "file manager" is a page in the admin UI |
| 41 | If object storage is needed later: **versitygw** | It puts an S3 API over *plain files*, so testcases stay greppable and git-versionable |

## Contest rules

| # | Decision | Reasoning |
|---|---|---|
| 42 | **Each question owned by exactly one participant** | The load-bearing rule — almost everything else follows from it |
| 43 | Equal starting balance; fixed increment X; no bidding above balance | |
| 44 | Questions, money and hints are **non-transferable** | Prevents collusion redistributing advantage |
| 45 | Score by **difficulty, binary solved/not** | No partial credit |
| 46 | **Tiebreak by earliest**, timestamped at **submission** | Judging latency then never affects fairness |
| 47 | **No penalty** for wrong submissions | Participant's explicit decision |
| 48 | Bounded by **one in flight + 3s cooldown** | A technical limit, not a scoring change; caps concurrent load at ~20 |
| 49 | Hints are **author-written text only** — hidden testcases are never revealed, at any price | Closes the exploit where a participant submits deliberately bad code, buys each revealed failing testcase, and hardcodes answers rather than solving |
| 50 | Hints purchasable **any time you own the question** | Otherwise someone stuck at minute 12 has 78 minutes of dead air and money they cannot use |
| 51 | Mid-contest edits allowed → **rejudge all submissions** for that question | |
| 52 | Rejudge is honest; owner re-attempts; **no refund** | Blast radius is one person, and they keep the question |
| 53 | Feedback: verdict + testcase **number** only | Never `jury_detail`; compile output is fine, it's their own code |
| 53a | Bidding closes by a **countdown that restarts on every bid**; admin may set its duration, close manually, or disable it | A fixed timer makes the auction a reflex-and-latency contest decided by who clicks last |
| 53b | Unsold questions return in auction 2 at the **same base price** | Waiting is already punished by losing 90 minutes of solving time; time is the scarce resource, not money |
| 53c | In-flight limit and cooldown enforced **per account, server-side**; cooldown starts when a job ends *or is cancelled*; **one active session per account** | A second browser window would otherwise double throughput on a speed-tiebreak contest; kiosk lockdown is a physical control, not an enforcement point |
| 53d | Late rejudge harm is resolved at **administrator discretion** — refund, void, or let the verdict stand — recorded with a reason | "You may re-attempt" is not a remedy with five minutes left |
| 53e | **25 questions kept**; auction 2 reframed as a leftover-and-hint round | 25 ÷ 20 = 1.25 questions each, so few leftovers; authoring 20 more problems is not affordable |
| 53g | Competitors are **individuals** — one person, one account, one seat | The rules were written for individuals throughout; "team registration" in the backend doc was a leftover |
| 53h | Questions auctioned **one at a time, in sequence** | Parallel bidding would let you commit the same coins to two questions and win both; avoiding funds-reservation logic removes the hardest correctness problem in the backend |
| 53i | Running order is **admin-defined and published in advance** | Lets participants budget across the whole set, which is the auction skill the format is meant to measure. Easy→Hard would make hoarding correct; random replaces planning with gambling |
| 53j | Tiebreak is **sum of solve times**, lower wins | ICPC-familiar, and rewards consistent early solving rather than just finishing early |
| 53k | Solve time measured **from acquiring the question**, not contest start | A question bought in auction 2 cannot be attempted before ~minute 100; timing from contest start would make buying late strictly worse and kill auction 2 again |
| 53l | **First AC always** sets the solve time — even if a rejudge invalidated it and the participant re-solved | Simple and generous; a solve is sticky and a later WA never un-solves it |
| 53m | Submitting permitted **in every phase**, including during auctions | Phases govern bidding, not work; otherwise someone out of money watches an auction with nothing to do |
| 53n | **No ownership cap** by default; admin-configurable | The auction already prices hoarding — six Easies means six problems to solve in the same time |
| 53o | **Opening window** then unsold, for questions nobody bids on | The bid countdown only starts on the first bid, so a dud would otherwise sit open forever |
| 53p | Voiding refunds **question price and hints**, admin-overridable | Hints toward an unsolvable problem bought nothing |
| 53q | **Self-registration in the hall**, closed before auction 1 | Follows from LAN-only; the roster must be final before bidding since balances are equal |
| 53r | **Administrators can override anything**, with a recorded reason | No rule should be able to trap the contest in a bad state — but unlimited authority without an audit trail is what disputes feed on |
| 53s | Virtual money is an **integer** | Refunds and adjustments stay exact |
| 53f | Contest server is **LAN-only** | Closes the phone-on-mobile-data second-session vector for free |

## Still open

**Pricing values.** The *structure* is fixed — equal starting balance, per-tier base
prices and scores, a fixed increment X, per-hint prices. The **values** will be set
once the 25 problems exist and have been ranked by real difficulty, since the problem
set tells you more than any model. This is game design, not software: no amount of
correct code fixes bad pricing.

- Bid countdown duration and opening-window duration
- Final round duration
- Auction running order (per-contest configuration)
- Deployment topology and core count (deliberately deferred)
- Python reader API surface for checkers and validators

## Phase structure and Phase 1

| # | Decision | Reasoning |
|---|---|---|
| 60 | The competition is **two phases**: Phase 1 qualifying round, Phase 2 auction contest | Phase 2's `Auction 1 / Coding Round 1 / Auction 2 / Final Round` are **rounds inside Phase 2**, not peers of Phase 1 — the earlier naming collided |
| 61 | Phase 1 has **two sections**, run strictly in sequence with separate time limits: Logical Puzzles, then Hacking | From the Phase 1 rulebook. Section B is opened by an administrator, leaving room for a break or a fix |
| 61a | Section A answer types: MCQ single/multi, fill-blank, numeric, sequence, set, long text — each `auto`, `validator` or `manual` graded | Most questions need no marking; open-ended ones can be scored by an uploaded validator; the rest are read by an evaluator |
| 61b | Short answers are marked on **the correctness of the reasoning** | Straight from the rulebook |
| 61c | Section B: participants submit a **test input**, never code; the given solution is shown, the reference solution never is | Reading the flawed solution is the task |
| 61d | **One scoring hack per given solution** | Points per hack alone would reward farming a single bug with near-identical inputs |
| 61e | Hack feedback is valid/invalid and hacked/not — never the verdict or the expected output | Otherwise the judge becomes an oracle for probing behaviour rather than a check on reading the code |
| 61f | Section A validators score **correctness**; the browser checks **format** only | Live correctness feedback would turn "find as many as you can" into brute force against the validator |
| 61g | Phase 1 selects who advances; an administrator chooses from the leaderboard, with the basis announced beforehand | No automatic top-N. Unlimited discretion without a published basis is what disputes feed on |
| 61h | Phase 1 contributes **no points** to Phase 2, and everyone advances on an identical balance | Keeps US-B1-01 intact; an early lead must not compound into an auction advantage |
| 61i | Phase 1 **rank** breaks an exact tie in the final standings | Avoids joint first place without letting Phase 1 add score |
| 61j | Three roles: participant, evaluator, administrator; **one account, one role** | Evaluators grade without touching contest state, and nobody grades their own work |
| 61k | One session per account applies to **participants only** | It is an anti-cheat control; applied to admins it would log an organiser out mid-auction |

## Architecture revisions

| # | Decision | Reasoning |
|---|---|---|
| 62 | **Redis dropped** — four services, not six | Sessions are in Postgres via Better Auth, the queue is a database poller, SSE fanout is in-process. One fewer thing to fail on the day |
| 63 | **Better Auth**, self-hosted, username + admin plugins | Database-backed sessions are revocable, which is what single-session enforcement needs; JWTs cannot be revoked. Works with no internet |
| 64 | **Next.js route handlers** for the backend, not NestJS | One deployable, Better Auth first-class, shared types with the UI for free |
| 65 | Solve time is **derived from submissions, never stored** | Satisfies "first AC always counts" and "recompute after a rejudge" simultaneously; no column can go stale |
| 66 | Auction deadlines are **database columns**, polled by a scheduler — never `setTimeout` | An in-memory timer cannot survive the restart NFR-B-10 requires |
| 67 | Realtime is **SSE**, not WebSockets | Every realtime flow is server→client; SSE brings reconnection with `Last-Event-ID` for free, which the reconnect stories require |
| 68 | Problems live on **one volume: backend read-write, judge read-only** | Publishing is the symlink swap the judge already treats as atomic. Amends judge assumption 4 |
| 69 | Samples are the **first K testcases**; the administrator sets K, the text is read from the package | A displayed sample can never drift from the testcase actually judged |
| 70 | **Automatic database backups with a tested restore** | Every other recovery story covers a *client* failing; this is the only cover for the *server* failing |
| 71 | Phase 1 needs **two new judge endpoints** — `/hack` and `/validate-answers` | Both are "run something in the sandbox against data supplied in the request", the one shape the judge did not offer |
